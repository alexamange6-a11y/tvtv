# Диапазоны штатного USB-обновления

Этот этап исследует путь обновления из работающего меню eCos. Он отличается от загрузочного `/recovery2.rcv`, описанного в [UPGRADE_RECOVERY_RU.md](UPGRADE_RECOVERY_RU.md).

## Подтверждённая цепочка вызовов

В обработчике `0x9002F2F8` после проверки выбранного файла вызывается USB-валидатор `0x9002E940` по `0x9002F3C8`. При ненулевом результате управление идёт через `0x9002F4F0` к подготовке `0x9002F09C`. В этой подготовке:

- `0x9002F22A` читает номер выбранного раздела из структуры состояния;
- `0x9002F22E` вызывает функцию расчёта диапазона **`0x9002E3E0`**;
- `0x9002F23E..0x9002F240` передаёт сообщение **`0x8F`** через диспетчер `0x9002DDD8`.

Таблица действий по `0x904AF4F4` содержит 133 пары номер/обработчик. Пара по `0x904AF774` равна `0x8F → 0x9002B02C`. Инициализация `0x9002DD6C` переносит обработчики в таблицу RAM `0x9064AFE0`; диспетчер индексирует её номером действия и выполняет косвенный вызов. Тело `0x9002B02C` выделяет объект сообщения, копирует 12 байт параметров и передаёт его через `0x90361114`.

Это подтверждает передачу рассчитанного диапазона в подсистему сообщений. Потребитель сообщения, окончательная запись SPI и возможные дополнительные ограничения пока не прослежены полностью. Ни один результат ниже не означает, что запись на устройстве уже проверена.

## Выполнен исходный расчёт диапазонов

Функция `0x9002E3E0` получает закэшированную OEM-таблицу через `0x9038200C`, сравнивает имена BOOT/DATA и суммирует **вместимости** разделов. Исходные инструкции функции исполняются целиком в `UpgradeRangeRunner`, включая возврат, стек и сохранённые регистры.

Выделение памяти, очистка, освобождение и сервис OEM-таблицы заменены явными заглушками. Для сервиса создана модель нужных полей: count, имена, capacity и start из проверенной заводской таблицы; внутренние записи имеют шаг 45 байт. Сам OEM-декодер здесь не выполняется. Сравнение строк использует читаемые из исходного eCos строки BOOT и DATA.

| Числовой выбор | Начало | Длина | Область рассчитанного диапазона |
|---|---|---|---|
| 0 («Все») | `0x000000` | `0x3F0000` | BOOT, TABLE, LOGO, V_OEM, KERNEL, ROOT, DATA; без AD |
| 1 | `0x000000` | `0x380000` | BOOT и код/ресурсы; без DATA/AD |
| 2 | `0x380000` | `0x070000` | Весь DATA |
| 3 и другие неподдерживаемые значения | — | — | Ошибка `0xFFFFFFFF` |

Названия и доступность вариантов 1/2 в интерфейсе именно устройства пользователя ещё не подтверждены. Таблица не служит рекомендацией выбирать их в меню.

Даже когда used у DATA равно 1, рассчитанная длина для этого раздела — **`0x70000`**. Это согласуется с тем, что USB-дамп содержит конфигурацию далеко за первым байтом. Нельзя собирать образ, сохраняющий только used-байт DATA.

## Практическое следствие

Предыдущий вывод «BOOT сохраняется» относится только к найденному циклу **загрузочного recovery**. Расчёт штатного варианта «Все» включает **BOOT и DATA**. Нельзя переносить свойства recovery-цикла на обновление из меню или считать, что любой способ установки автоматически сохраняет настройки и загрузчик.

До выдачи изменённого BIN остаётся установить конечного потребителя сообщения, подтверждённые ограничения записи/совместимости, возможность восстановления и работу нового GUI. Текущая сборка лишь записывает проверенные диапазоны и доказательства в `build/upgrade/findings.json`; никакой записи SPI или готового BIN не выполняется.

## Проверки

Три новых теста исполняют оригинальную функцию для всех трёх допустимых вариантов и нескольких неподдерживаемых значений, проверяют расчёт по capacity, возврат и ABI. GNU-листинги соответствующих блоков включены в результаты аудита. Все проверки повторяются через обычный `build.bat`.
