# USB-проверки и загрузчик: подтверждённый следующий этап

Исследованы реальные инструкции поддерживаемого заводского BIN и eCos. Результаты повторяет `tools/upgrade_audit.py`; он проверяет SHA256 входных файлов, адреса инструкций, литералы и таблицу драйвера. Модуль включён в обычный `build.bat`. Он создаёт `build/upgrade/findings.json`, а при наличии GNU CK610 objdump — листинги `build/upgrade/disassembly/`. Файл для прошивки или восстановления не создаётся.

## Независимая CRC таблицы разделов

Последние четыре байта таблицы, **`0x201FC..0x201FF`**, содержат big-endian **`B51B6607`**. Это стандартная CRC32 с начальным seed=0 от **508 байт `0x20000..0x201FB`**. Она отличается от нулевого CRC-слота раздела TABLE по `0x201A1`.

Проверка подтверждена в исходной функции eCos `0x9002E940`:

| Инструкция | Действие |
|---|---|
| `0x9002EB26` | seed=0 |
| `0x9002EB28..0x9002EB2E` | адрес заголовка в стеке и длина 508 |
| `0x9002EB30` | вызов реальной CRC-функции `0x900CCBCC` |
| `0x9002EB38..0x9002EB3C` | сравнение с ранее декодированным CRC; при несовпадении переход к отказу `0x9002EE20` |

Тестовый интерпретатор выполняет эти исходные инструкции, саму CRC-функцию и её ROM-таблицы. Сетевые/GUI-заглушки в этом пути не используются. Оригинал проходит, изменение поля CRC KERNEL с прежней CRC заголовка отклоняется, повторный расчёт CRC заголовка восстанавливает прохождение **этого блока**. Дополнительно функция проверена на стандартных векторах, разных начальных seed и выравнивании 0..3.

Ранее выполненное чтение заголовка и big-endian декодирование поля моделируются входным состоянием; весь USB-валидатор, OEM-проверки и запись флеш-памяти не исполняются. Принятие CRC-блока не означает принятия всего обновления.

`tools/formats.py` и `tools/dump_analysis.py` теперь обязательно проверяют эту сумму. При точной пересборке оригинала она пересчитывается после внешних сумм разделов. Функция `update_partition_table_crc` возвращает только 512-байтный заголовок, не полный модифицированный BIN.

В исходном заголовке байты +`0x1F9..0x1FB` равны `01 01 66`. Проверка по `0x9002EB44..0x9002EB48` при нулевом +`0x1FA` пропускает последующие проверки payload/OEM, но выполняется **после CRC заголовка**. Проект сохраняет эти байты без изменений и не использует отключение проверок. Назначение +`0x1F9`/`0x1FB` и остальных vendor-полей полностью не установлено.

## Реальная функция USB-восстановления

У загрузчика две адресные области. Начальная часть сопоставляется как `адрес = смещение файла + 0x100000`. Затем SPI-чтение из смещения `0x2000` копирует `0x1E000` байт в RAM `0x93F60000`, после чего выполняется переход в `0x93F60400`. Поэтому для этой части правильная формула: **`адрес = смещение файла + 0x93F5E000`**. Ошибка на `0x2000` даёт неверные адреса функций.

Функция восстановления находится по **`0x93F72360`**, смещение файла **`0x14360`**. Это подтверждено вызовом из wrapper `0x93F67784` и разбором тела функции. Wrapper записывается в callback по `0x93F677A8`; основной код загрузчика читает callback и вызывает его при ненулевом адресе по `0x93F60478`. Фактическая доступность этого пути и поведение на приставке пользователя не проверены.

По `0x93F723D4` загружается указатель на строку **`/recovery2.rcv`**, затем по `0x93F723DA` вызывается чтение файла в буфер с пределом 4 МиБ. Прослежены wrapper-функции до FAT-читателя `0x93F72D94`. В нём найдены чтение размера FAT directory entry и ограничение максимальной длины, описанные ниже. Полная проверка формата образа до записи не установлена. Обнаруженное имя файла **не является инструкцией переименовать BIN и вставить флешку**.

После чтения функция ждёт IR-код, сравнивает его с несколькими константами и допускает ветку записи. Соответствие этих констант кнопкам физического пульта не подтверждено.

## Проверка длины: подтверждён недостаточный барьер

FAT-читатель берёт размер файла из directory entry +`0x1C` по `0x93F7350A`. В блоке `0x93F735A8..0x93F735C2` вычисляется конец чтения как `min(смещение + запрошенная длина, размер файла)`; при смещении не меньше размера используется путь нулевого результата `0x93F73704`. Ошибка возвращает `-1`, обычный результат — число прочитанных байтов из r9 по `0x93F73712`.

В вызывающем коде **`0x93F723DC..0x93F723DE`** результат сравнивается только с **`-1`**. Любое иное значение переходит дальше к `0x93F723E8`. В этом барьере нет проверки на `>=0x3F0000`, хотя последующий цикл записи использует буфер до этого смещения.

Тесты исполняют исходные блоки с результатами `-1`, `0`, `1`, `0x3EFFFF`, `0x3F0000`, `0x400000`: только `-1` отклоняется. Отдельно исполняется ограничение длины для пустых, коротких, нормальных и превышающих 4 МиБ файлов. Размер, параметры и результат чтения подаются как уже полученные значения; весь FAT-читатель, directory lookup и чтение USB не эмулируются.

Это означает, что **само обнаружение recovery-файла и прохождение этого перехода не подтверждают пригодность образа**. Пустой или усечённый файл нельзя считать безопасным из-за отсутствия сообщения об ошибке. Это дополнительная причина не выдавать неподтверждённый recovery-файл и не предлагать пробную запись.

## Подтверждённый диапазон записи

Ветка `0x93F725BE` задаёт начало `0x20000`, число блоков 61 и конец `0x3F0000`. Цикл `0x93F72466..0x93F72494` вызывает стирание и запись блоками `0x10000`:

| Диапазон флеш-памяти | Действие именно этого цикла |
|---|---|
| `0x000000..0x01FFFF` — BOOT | Сохраняется |
| `0x020000..0x37FFFF` — TABLE, LOGO, V_OEM, KERNEL, ROOT и промежутки | Записывается |
| `0x380000..0x3EFFFF` — DATA | **Записывается целиком** |
| `0x3F0000..0x3FFFFF` — AD | Сохраняется |

Источник каждой записи — `буфер + абсолютное смещение флеш-памяти`. Нельзя сдвигать образ, убирая из него BOOT. Нельзя подставлять заводской пустой DATA вместо конфигурации устройства.

Dispatch-wrapper стирания `0x93F68514` обращается к слоту +`0x0C` выбранного SPI-драйвера; wrapper записи `0x93F68534` — к +`0x10`. Таблица по `0x93F74714` указывает соответственно на `0x93F6DA90` и `0x93F6DB20`; в телах подтверждены SPI-команды D8 (стирание) и 02 (программирование).

Тесты выполняют исходные инструкции настройки диапазона и всех 61 итерации, проверяя чередование стирания/записи, размер, адрес источника, полное покрытие DATA и отсутствие обращений к BOOT/AD. SPI, дисплей и вывод сообщений заменены записывающими заглушками. Реальная флеш-память не затрагивается.

Полученный USB-дамп `0x3F0000` содержит весь диапазон, из которого **данный цикл** берёт байты. Его неполный размер сам по себе не исключает пригодность для этого пути. Однако найденный барьер длины недостаточен, полная проверка формата и физическое восстановление не подтверждены, поэтому проект не превращает дамп в готовый recovery-файл. Для независимого аппаратного восстановления по-прежнему нужен полный SPI-дамп с подтверждённой микросхемой и напряжением.

## Что ещё нужно установить

1. Полная проверка формата recovery-файла и остальные пути обновления; найденное сравнение результата чтения не обеспечивает минимальный размер.
2. Условия регистрации/вызова recovery-callback и подтверждающие кнопки конкретного пульта.
3. Реальное восстановление устройства и сохранение его DATA.
4. Работа нового GUI, возврат из приложений и воспроизведение YouTube на устройстве.

Повторная офлайн-проверка после подготовки проекта:

```bat
.venv\Scripts\python.exe tools\upgrade_audit.py
```

Команда не требует сети или подключённой приставки.
